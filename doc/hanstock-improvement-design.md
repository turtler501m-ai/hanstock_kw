# 한스톡 개선 설계

## 1. 목적

한스톡을 기능이 많은 자동매매 도구에서 **주문 결과를 재현할 수 있고, 장애 시 신규 위험을 자동 차단하며, 전략 성과를 신뢰할 수 있는 운영 플랫폼**으로 개선한다.

이 문서는 국내주식 한스톡을 우선 범위로 한다. 미국주식 미스톡은 공통 계약을 재사용하되 별도 DB와 시장 규칙을 유지한다. 주문·체결 상세 설계는 `dockw/D1.기능구현1.md`, 미스톡 화면 이식은 `doc/mistock-dashboard-parity-plan.md`를 하위 설계로 사용한다.

## 2. 현재 진단

### 강점

- 키움 국내·미국주식 어댑터와 브로커 중립 계약이 존재한다.
- 승인, 자율매매, 위험 예약, 포지션 보호, 시장 국면 기능이 이미 분리돼 있다.
- 주문 체결 자동 동기화와 수동 동기화 경로가 있고 회귀 테스트가 폭넓다.
- 기본 운영값이 모의투자·DRY RUN·수동 승인으로 닫혀 있다.

### 핵심 문제

1. 일반 주문의 `trades`와 자율매매의 `ai_managed_orders`/`ai_managed_fills`가 서로 다른 원장을 사용한다.
2. 주문 접수, 체결, 잔고 보정이 일부 흐름에서 같은 거래 레코드에 표현된다.
3. `src/dashboard/core.py`, `routes/stock_order.py`, `routes/mistock.py`가 큰 조립 모듈이 되어 변경 영향 범위가 넓다.
4. `order_sync_service`가 명시적 의존성 대신 대시보드 전역 객체를 동적으로 가져와 독립 테스트와 재사용이 어렵다.
5. DB 생성과 컬럼 추가가 여러 저장소의 런타임 초기화에 흩어져 있어 스키마 버전, 롤백, 배포 전 검증이 불명확하다.
6. 전략의 신호 품질과 실주문 품질을 한 흐름으로 추적하기 어렵고, 비용 미확인 거래는 순성과의 신뢰도를 낮춘다.

## 3. 목표 구조

```text
전략/수동요청
    -> TradeIntent
    -> MarketPreflight + RiskDecision
    -> Approval
    -> OrderService
    -> BrokerAdapter
    -> Order/Fills 원장
    -> Position Projector
    -> Reconciliation
    -> 성과/대시보드/알림
```

### 계층별 책임

| 계층 | 책임 | 금지 사항 |
|---|---|---|
| Strategy | 신호와 주문 의도 생성 | DB 직접 주문 기록, 브로커 직접 호출 |
| Application | 승인, 리스크, 주문 상태 전이 조정 | 키움 응답 필드 직접 해석 |
| Broker | 시장별 조회·주문과 응답 정규화 | 전략 판단, 성과 계산 |
| Ledger | 주문·이벤트·체결의 영속화와 멱등성 | 잔고 차이를 임의 체결로 생성 |
| Projection | 체결로 포지션·성과 계산 | 원본 이벤트 수정 |
| Dashboard | 조회 모델 표시와 명령 전달 | 거래 규칙 중복 구현 |

## 4. 우선 개선 과제

### P0. 단일 주문 원장과 복구 게이트

모든 주문 경로가 공통 `OrderService`를 통과하게 한다. 신규 테이블은 `orders`, `order_events`, `fills`, `reconciliation_adjustments`로 구성하고 기존 테이블은 전환 기간 동안 호환 조회로 유지한다.

필수 불변조건:

- 동일 `client_order_key`의 브로커 제출은 최대 1회다.
- 브로커 주문번호를 받지 못한 timeout은 `broker_unknown`이며 자동 재주문하지 않는다.
- `filled_qty`는 감소하지 않고 요청수량을 넘지 않는다.
- 포지션 수량은 검증된 체결만으로 바뀐다.
- 계좌 불일치, 오래된 시세, 미보호 포지션, 결과불명 주문이 있으면 신규 위험 주문을 차단한다.
- 취소 중 발생한 체결도 먼저 반영한 뒤 잔량을 계산한다.

기동 상태를 `RECOVERING -> REDUCE_ONLY -> READY`로 명시한다. 미결 주문, 누락 체결, 포지션, 보호 주문의 대조가 끝나기 전에는 `READY`가 될 수 없다.

완료 기준:

- 일반·수동·스케줄·자율 주문이 같은 상태 머신을 사용한다.
- 재시작, timeout, 부분체결, 중복 클릭 테스트를 통과한다.
- 모의계좌 10거래일 동안 중복 주문과 설명 불가 수량 차이가 0건이다.

### P0. 승인 화면을 운영 콘솔로 전환

승인 상태와 주문 상태를 분리하고 대기·진행·완료·오류 탭으로 나눈다. 기본 화면에는 대기와 진행만 표시한다.

승인 카드 필수 정보:

- 요청/체결/잔여 수량, 주문유형, 주문가, 평균체결가
- 신호가와 현재가, 시세 기준시각, 승인 만료시각
- 현재/주문 후 종목 비중, 주문 가능 현금, 미체결 예약금액
- 손절가, 목표가, 최대 위험금액, 보호 방식
- 시장 국면, 리스크 검사 결과, 차단 사유
- 승인·결정·내부주문·브로커주문 상관 ID

일괄 작업은 기본 선택을 0건으로 하고 만료된 신호의 재처리를 금지한다. 재처리는 기존 승인을 되살리지 않고 현재 데이터로 새 의도와 승인을 만든다.

### P1. 애플리케이션 경계 정리

`dashboard/core.py`는 FastAPI 생성과 의존성 조립만 담당하도록 축소한다.

권장 패키지:

```text
src/application/orders/
    service.py
    state_machine.py
    reconciliation.py
    preflight.py
src/application/portfolio/
    positions.py
    risk.py
src/dashboard/read_models/
    approval_queue.py
    operations.py
src/db/migrations/
```

라우트는 요청 검증, 서비스 호출, 응답 변환만 수행한다. 서비스에는 `OrderRepository`, `Broker`, `Clock`, `Notifier`를 생성자 인자로 주입한다. 전역 객체 복사나 라우트에서의 SQL 실행은 금지한다.

완료 기준:

- 신규 라우트 함수는 거래 규칙을 포함하지 않는다.
- 주문 동기화 서비스는 `dashboard.core`를 import하지 않고 단위 테스트할 수 있다.
- 대형 모듈은 기능 단위로 점진 분리하되 외부 API 계약은 유지한다.

### P1. 버전형 DB 마이그레이션

런타임의 산발적인 `ALTER TABLE`을 순서가 보장되는 마이그레이션으로 이동한다.

- `schema_migrations(version, applied_at, checksum)`을 둔다.
- 각 마이그레이션은 재실행 가능 여부와 사전·사후 검증 SQL을 갖는다.
- 배포 전 운영 DB 백업과 dry-run 검사 결과를 남긴다.
- 파괴적 변경은 추가 -> 이중 기록 -> 백필 -> 조회 전환 -> 구 컬럼 제거 순서로 수행한다.
- 운영 시작 시 코드가 요구하는 스키마보다 낮거나 높으면 거래 엔진을 fail-closed한다.

### P1. 운영 관측성과 감사

모든 흐름에 `correlation_id`, `decision_id`, `approval_id`, `order_id`, `broker_order_id`를 연결한다. 로그 문자열뿐 아니라 구조화된 이벤트로 기록한다.

운영 화면의 핵심 지표:

- 엔진 상태와 마지막 heartbeat
- 마지막 성공 동기화 및 데이터 지연
- 상태별 활성 주문 수와 최고 체류시간
- 결과불명 주문, 계좌 불일치, 미보호 포지션 수
- 당일 주문/체결/거부/부분체결, 실현·평가손익
- Kill Switch 상태, 변경자, 사유, 시각

즉시 알림은 신규 위험을 멈춰야 하는 사건과 단순 정보 알림을 등급으로 분리한다. 알림 실패는 주문 결과를 바꾸지 않지만 별도 운영 장애로 누적한다.

### P2. 전략 품질 게이트

전략 결과를 `signal -> decision -> plan -> approval -> order -> fill -> pnl`로 추적한다. 전략 버전과 사용한 시장 데이터 시각을 고정한다.

배포 전 전략 검증:

- 미래 데이터 참조 방지와 확정봉 규칙 검사
- 수수료·세금·슬리피지를 포함한 워크포워드 검증
- 종목 생존편향과 거래정지 데이터 처리
- 국면별 성과, MDD, 회전율, 체결률 검토
- shadow 결과와 실제 결과의 차이 측정

자동 중단 조건은 최소 거래 수를 충족한 뒤 MDD, 연속 손실, 기대값, 체결 품질 기준으로 판정한다. 자동 중단은 신규 진입만 막고 보호·청산은 허용한다.

### P2. 성과 원장 재구축

성과는 검증된 체결과 현금흐름에서 계산한다. 총 입금액 대비 수익률과 전략 성과를 분리한다.

- 실현/평가손익, 수수료, 세금, 슬리피지 분리
- `broker`, `estimated`, `unavailable` 비용 출처 표시
- 종목·전략·시장 국면별 기여도
- TWR, MDD, Profit Factor, 기대값, 자본 사용률
- 미확인 체결이나 비용 누락 시 `estimated` 배지 표시

### P3. 국내·미국 공통화

공통화 대상은 주문 의도, 상태 머신, 승인, 위험 판정 결과, 감사 이벤트다. 가격 정밀도, 통화, 거래시간, 세금, 지원 주문유형, 체결 식별자는 시장 capability로 분리한다. 미국주식 기능은 국내 원장을 그대로 복사하지 않고 동일 계약의 별도 구현으로 연결한다.

## 5. API 초안

| Method | Path | 역할 |
|---|---|---|
| GET | `/api/orders` | 상태·거래일·전략별 주문 조회 |
| GET | `/api/orders/{id}` | 주문 이벤트와 체결 상세 |
| POST | `/api/orders/{id}/approve` | 최신 데이터 재검사 후 승인 |
| POST | `/api/orders/{id}/cancel` | 멱등 취소 요청 |
| POST | `/api/orders/{id}/reconcile` | 브로커 상태 명시적 재조회 |
| GET | `/api/operations/health` | 거래 준비 상태와 차단 사유 |
| GET | `/api/reconciliation/issues` | 계좌·주문·포지션 불일치 조회 |

쓰기 API는 `Idempotency-Key`, 기대 버전, 요청자, 사유를 받는다. 동시 변경이면 `409 Conflict`, 안전 게이트 차단이면 원인 코드와 사용자 조치를 반환한다.

## 6. 구현 로드맵

### 0단계: 기준선 고정 — 2~3일

- 기존 상태·API·DB 데이터 사전 조사 도구 작성
- 주문/체결/잔고 불변조건 리포트 생성
- 실제 장애 사례를 익명화된 fixture와 회귀 테스트로 고정

### 1단계: 관찰 전용 원장 — 1~2주

- 마이그레이션 체계와 신규 원장 추가
- 기존 주문 결과를 신규 원장에 shadow 기록
- 기존/신규 상태 차이 대시보드 제공
- 실제 주문 경로는 변경하지 않음

### 2단계: 공통 주문 서비스 — 2주

- 수동 승인 한 경로부터 공통 서비스로 전환
- 멱등성, timeout 복구, 부분체결, 취소 구현
- 모의계좌와 장애 주입 검증 후 스케줄·전략 경로 순차 전환

### 3단계: 복구·리스크·운영 콘솔 — 1~2주

- 기동 복구 게이트와 reduce-only 모드
- 통합 preflight와 위험 예약
- 승인 콘솔, 감사 흐름, 운영 알림 적용

### 4단계: 성과·전략 품질 — 1~2주

- 체결 기반 포지션·비용·성과 projection
- 전략 버전별 live/shadow 성과와 자동 중단 기준 적용
- 미스톡 읽기 전용 운영실 연결

## 7. 테스트 전략

필수 테스트 층:

1. 상태 머신의 모든 허용·금지 전이
2. DB UNIQUE와 낙관적 잠금을 포함한 동시성
3. timeout, 응답 유실, DB 저장 실패, 재시작 장애 주입
4. 키움 응답 fixture 기반 브로커 계약
5. 포지션·현금·위험 예약 불변조건
6. 라우트와 프런트엔드 DOM/API 계약
7. 구 DB에서 신규 스키마로의 마이그레이션
8. 모의계좌 장중 및 장마감 reconciliation

네트워크 호출은 테스트에서 전부 mock한다. 시간과 거래일 판정에는 주입 가능한 `Clock`을 사용한다.

## 8. 배포와 롤백

- 기본값은 계속 `DRY_RUN=true`, `TRADING_ENV=demo`, `ENABLE_LIVE_TRADING=false`, `REQUIRE_APPROVAL=true`로 유지한다.
- 각 단계는 `observe_only`, `shadow`, `demo_limited`, `demo_full`, `live_limited` 기능 플래그로 전환한다.
- 롤백은 코드만 되돌리고 신규 원장 데이터는 삭제하지 않는다.
- 신규 서비스 장애 시 기존 경로로 자동 우회하지 않는다. 중복 주문 위험 때문에 신규 진입을 중단하고 운영자 판단을 요구한다.
- 배포 후 스키마, heartbeat, 동기화, broker_unknown, reconciliation 지표를 자동 점검한다.

## 10. 첫 번째 개발 묶음

첫 구현은 화면 개편보다 아래 순서로 제한한다.

1. 버전형 마이그레이션 기반과 `orders`, `order_events`, `fills` 추가
2. 기존 수동 승인 주문의 shadow 기록
3. 상태 차이와 불변조건을 확인하는 진단 API
4. timeout·부분체결·중복 승인 회귀 테스트
5. 모의계좌에서 차이 0건을 확인한 뒤 수동 승인 경로 전환

이 묶음이 완료돼야 리스크 화면, 실시간 UI, 전략 자동화 확대가 신뢰할 수 있는 데이터 위에서 동작한다.

## 11. 2026-08-28 구현 재점검

앞선 “전체 완료” 평가는 정확하지 않았다. 현재 반영 수준은 아래와 같다.

| 영역 | 반영 수준 | 상태 |
|---|---:|---|
| 버전형 마이그레이션과 신규 주문 원장 | 90% | 구현·테스트 완료, 기존 스키마 전체 이전은 미완료 |

## 12. 2026-08-28 최종 코드 반영 결과

이번 재점검에서 남아 있던 코드 범위를 다음과 같이 반영했다.

- 국내 승인 생성 경로를 하나의 팩토리로 통합하고 일반 전략, AI 주식, 내러티브 전략, 대시보드가 동일한 주문 원장을 생성하도록 연결했다.
- 일반 전략의 즉시 실주문도 `approved -> submitting -> submitted/rejected/broker_unknown` 상태 전이를 기록하도록 전환했다.
- 서버 기동 시 `recovering` 상태를 먼저 기록하고 저장된 불변조건 검사 결과에 따라 `reduce_only` 또는 `ready`로 전환한다. FastAPI 외 실행 경로도 최초 위험 주문 전에 같은 복구 검사를 수행한다.
- 마이그레이션 2에 주문 런타임 상태와 체결 기반 `positions` 투영 테이블을 추가했다.
- 누적 평균 체결가에서 증분 체결가를 역산해 체결을 중복 없이 저장하고, 검증된 체결만으로 보유수량과 순현금흐름을 다시 계산한다.
- 주문/체결/완료시각/브로커 주문번호 불변조건 검사 도구와 회귀 테스트를 보강했다.

코드 및 로컬 검증 범위는 완료됐다. 단, “모의계좌 최소 10거래일”은 시간 경과와 실제 브로커 운영이 필요한 배포 후 승인 조건이므로 코드 완료율과 분리한다. 실계좌 활성화 전 이 운영 증적을 반드시 확보해야 한다.

## 13. 재감사 및 추가 보강 결과

최종 보고 후 주문 호출 지점을 다시 전수 대조해 다음 누락을 발견하고 보강했다.

- `managed_order_id`가 있는 자율매매 승인이 통합 원장 생성을 건너뛰던 문제를 제거하고 승인·제출 결과를 양쪽 상태 머신에 동기화했다.
- 미국주식 실행 주문도 Mistock DB 안에서 국내와 같은 마이그레이션, 주문 상태, 이벤트, 체결, 포지션 계약을 사용한다.
- 미국주식 주문·체결 포지션·운영 건강 상태 조회 API를 추가했다.
- 오래 동기화되지 않은 활성 주문과 Kill Switch를 단순 경고가 아닌 신규 위험 차단 조건으로 승격했다.
- 브로커 상태 별칭을 정규화하고 허용하지 않는 상태 및 상태 전이를 거부한다.
- 계좌·시장·브로커 주문번호 조합에 DB UNIQUE 제약을 추가했다.
- AI 자동화와 주문 라우터 테스트 DB를 격리해 로컬 운영 원장 오염을 방지했다.

현재 코드 반영 수준은 안전 주문 원장·승인·복구 게이트·국내/미국 공통 계약 기준 약 90%로 평가한다. 남은 10%는 코드 누락이 아니라 다음 운영/장기 구조 개선 범위다.

- 모의계좌 최소 10거래일 동안 중복 주문, 원인 불명 체결, 잔고 차이 0건을 증명하는 운영 관찰
- `dashboard.core` 호환 계층과 기존 `trades`, `ai_managed_orders`, Mistock `managed_orders` 투영을 완전히 제거하는 장기 마이그레이션
- 체결 수수료·세금 원천값이 제공되는 브로커 환경에서 실현손익/TWR/MDD 장기 성과 검증

이 항목들은 기존 동작과 데이터의 단계적 폐기가 필요하므로 이번 안전 개선에서 강제 삭제하지 않는다. 특히 운영 증적이 확보되기 전에는 실계좌 활성화를 완료로 판정하지 않는다.
