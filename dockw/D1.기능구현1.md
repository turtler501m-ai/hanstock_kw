
• 빠짐없이 안전하게 적용하려면 “기능을 한꺼번에 추가”하는 방식이 아니라, 주문 원장을 먼저 바로잡고 모든 주문 경로를 하나의 상태 머신으로 통합한 뒤 단계적으로 전환해야 합니다. 순서를 바꾸면 잘못된 원장 위에 리스크·성과 기능을
쌓게 됩니다.

## 기본 원칙

- 키움 원본을 주문·체결 상태의 최종 진실로 사용
- 주문, 체결, 포지션, 잔고 조정을 별도 원장으로 분리
- 모든 주문 경로가 동일한 주문 서비스와 상태 머신 사용
- Timeout이나 응답 누락 상태에서는 절대 자동 재주문하지 않음
- 잔고 차이를 임의의 매수·매도 체결로 만들지 않음
- 기존 기능은 즉시 제거하지 않고 병행 검증 후 전환
- 실계좌 적용 전 모의계좌에서 충분한 거래일 동안 무인 검증

## 1단계: 요구사항을 추적 가능한 작업으로 고정

먼저 사용자가 제시한 모든 항목을 요구사항 ID로 만들어야 합니다.

예:

- ORD-001: 주문 접수와 체결 분리
- ORD-002: 부분체결 누적 반영
- ORD-003: 중복 주문 방지
- ORD-004: Timeout 결과 불명 처리
- ORD-005: 정정·취소 경쟁 처리
- POS-001: 증권사 포지션과 내부 포지션 대조
- RISK-001: 일손실 한도
- MKT-001: 거래시간 및 휴장일
- DATA-001: 시세 신선도 검사
- PERF-001: 수수료·세금 포함 순손익

각 요구사항에는 반드시 다음이 있어야 합니다.

- 구현 위치
- 정상 시나리오
- 실패 시나리오
- 자동 테스트
- 운영 확인 지표
- 완료 조건
- 배포 단계

이 추적표가 있어야 “빠진 기능이 없는지” 객관적으로 확인할 수 있습니다.

## 2단계: 주문·체결 데이터 모델 재설계

현재 trades 테이블 하나에 주문, 체결, 잔고 보정이 섞인 구조를 분리해야 합니다.

권장 구조:

### orders

주문 의도와 증권사 주문 상태를 관리합니다.

- 내부 주문 ID
- client_order_key
- 계좌 ID
- 시장
- 종목
- 매수·매도
- 주문 유형
- 요청수량
- 주문가격
- Stop 가격
- TIF: DAY/IOC/FOK
- 전략 ID와 버전
- 신호 ID
- 승인 ID
- 증권사 주문번호
- 현재 상태
- 생성·제출·완료·만료 시각
- 마지막 오류

### order_events

주문 상태 변경을 수정 불가능한 이벤트로 기록합니다.

- 주문 생성
- 리스크 승인
- 제출 시작
- API 요청
- 주문번호 수신
- 부분체결
- 정정 요청
- 취소 요청
- 완전체결
- 거부
- 만료
- 결과 불명
- 복구 완료

### fills

실제 체결만 저장합니다.

- 증권사 체결 식별키
- 주문 ID
- 개별 체결수량
- 개별 체결가격
- 누적 체결수량
- 수수료
- 세금
- 체결시각
- 증권사 원본 응답

증권사 체결 식별키에 UNIQUE 제약을 걸어 같은 체결이 두 번 반영되지 않게 해야 합니다.

### positions

실제 체결로부터 계산된 내부 포지션입니다.

- 계좌
- 종목
- LONG/SHORT
- 보유수량
- 매도 가능수량
- 평균단가
- 실현손익
- 보호수량
- SL/TP
- 진입시각
- 전략 귀속

### position_attributions

실제 계좌 보유수량을 전략별로 배분합니다. 전략 귀속 변경은 실제 매매가 아니므로 fills에 넣으면 안 됩니다.

### reconciliation_adjustments

잔고 차이와 관리상 보정만 저장합니다.

- 차이 수량
- 차이 사유
- 증권사 잔고 스냅샷
- 내부 예상수량
- 자동 확정 여부
- 검토 상태

잔고 조정은 주문내역·체결내역·실현손익에 직접 포함하지 않아야 합니다.

### account_snapshots, market_snapshots

계좌·시세 데이터를 기준시각과 함께 저장합니다. 주문 판단에 사용된 데이터가 무엇인지 재현할 수 있어야 합니다.

## 3단계: 단일 주문 상태 머신 구축

모든 전략이 다음 상태를 공통으로 사용해야 합니다.

CREATED
→ RISK_APPROVED
→ APPROVAL_PENDING
→ APPROVED
→ SUBMITTING
→ SUBMITTED
→ PARTIALLY_FILLED
→ FILLED

분기 상태:

SUBMITTING → BROKER_UNKNOWN
SUBMITTED → CANCEL_PENDING → CANCELED
PARTIALLY_FILLED → CANCEL_PENDING → CANCELED
CREATED/APPROVED → EXPIRED
각 유효 상태 → REJECTED

중요 규칙:

- SUBMITTING 선점에 성공한 프로세스만 API 호출
- BROKER_UNKNOWN은 실패가 아니며 재주문 금지
- 완전체결은 누적 체결수량 == 요청수량일 때만 설정
- 취소 상태에서도 추가 체결을 받을 수 있음
- 터미널 상태는 키움 원본 없이 이전 상태로 되돌리지 않음
- 모든 상태 전환은 예상 기존 상태를 조건으로 원자적으로 갱신
- 상태 전환마다 order_events 기록

기존 자율주문의 상태 머신을 확장해 일반 스케줄, 수동승인, AI 리밸런싱, 하이킨아시 주문도 동일한 경로로 보내는 것이 좋습니다.

## 4단계: 중복 주문 방지 표준화

모든 주문에 결정적인 client_order_key를 생성합니다.

예:

계좌 + 전략 + 전략버전 + 신호ID + 종목 + 매수매도 + 거래일 + 진입차수

보호 방법:

- DB UNIQUE 제약
- API 호출 전 SUBMITTING 상태 선점
- 동일 종목의 활성 위험 주문 검사
- 신호 자체에도 signal_key UNIQUE 적용
- 체결에는 fill_key UNIQUE 적용
- 재시작 후에도 같은 키를 다시 사용
- 키움이 사용자 주문 ID를 지원하면 함께 전달
- 같은 신호를 재처리하면 기존 주문 결과를 반환

종목만 기준으로 중복을 막으면 서로 다른 전략의 정상 주문까지 막을 수 있으므로, 주문키와 계좌 전체 노출 제한을 함께 사용해야 합니다.

## 5단계: Timeout·응답 누락 복구

주문 API는 자동 재시도하지 않습니다.

처리 순서:

1. 주문 호출 전에 SUBMITTING 저장
2. 정상 주문번호 수신 시 SUBMITTED
3. Timeout·연결 종료·응답 파싱 실패 시 BROKER_UNKNOWN
4. 같은 주문 자동 재전송 금지
5. 키움 주문내역에서 주문번호 또는 후보 주문 조회
6. 종목·구분·수량·가격·요청시간이 유일하게 일치하면 연결
7. 여러 후보가 있으면 결과 불명 유지
8. 운영 경고 및 신규 동일 주문 차단
9. 일정 시간이 지나도 확인되지 않으면 수동 검토
10. 실패가 확정된 경우에만 재주문 가능

응답 누락 주문을 잔고 차이만으로 바로 체결 처리해서는 안 됩니다.

## 6단계: 부분체결·정정·취소 정책

부분체결은 주문 상태가 아니라 운영 정책까지 정의해야 합니다.

전략별 설정 예:

- 최대 대기시간
- 최소 허용 체결률
- 잔량 유지 또는 취소
- 최대 정정 횟수
- 정정 가격 범위
- 장 마감 전 강제 취소 시각
- 부분체결 중 손절 발생 시 행동

손절 발생 시 권장 순서:

신규 진입 금지
→ 미체결 진입 잔량 취소
→ 취소 결과 확인
→ 이미 체결된 수량 확인
→ 체결수량만큼 청산 주문
→ 청산 체결 확인

취소 요청 중 추가 체결이 발생하면 최신 누적 체결수량을 먼저 반영하고 남은 수량만 취소된 것으로 계산해야 합니다.

정정 주문은 원주문과 연결 관계를 저장하고 수정 횟수를 제한해야 합니다.

## 7단계: 계좌·주문·포지션 동기화 재구축

동기화는 다음 세 원천을 같은 기준시각으로 읽어야 합니다.

- 증권사 잔고
- 증권사 당일 주문·미체결
- 증권사 체결내역

안전한 동기화 절차:

1. 동기화 시작시각 기록
2. 주문·체결 조회
3. 미체결 주문 조회
4. 잔고 조회
5. 다시 주문·체결 조회
6. 두 주문 조회 사이에 변경이 있으면 잔고 비교를 재시도
7. 일관된 스냅샷일 때만 대조
8. 활성 주문이 있는 종목은 잔고 차이 자동 보정 금지
9. 차이는 reconciliation_adjustments에 저장
10. 실제 체결로 확인된 경우에만 포지션 반영

프로그램 시작 시에는 반드시 복구 모드로 진입합니다.

신규 주문 차단
→ 미결 관리주문 복원
→ 증권사 미체결 조회
→ 누락 체결 반영
→ 잔고 대조
→ 보호 주문 대조
→ 불일치가 없을 때만 신규 주문 허용

불일치가 남으면 매도·취소 같은 위험 축소 행동만 허용해야 합니다.

## 8단계: 기존 데이터 정리

운영 DB는 바로 삭제하거나 다시 계산하면 안 됩니다.

현재 확인된 항목:

- 키움 주문번호 없는 보정 기록 396건
- 오래된 미결 기록 48건
- 수수료·세금 누락 기록 857건
- 오늘 생성된 가상 거래 9건

정리 절차:

1. 운영 DB 백업
2. 각 행을 broker_fill, broker_order, synthetic_adjustment, unknown으로 분류
3. 키움 주문번호가 있는 기록을 원본 주문내역과 대조
4. 실제 체결만 신규 fills로 이관
5. 잔고 보정은 reconciliation_adjustments로 이관
6. 과거 거래일 미체결은 키움 최종 상태와 대조
7. 확인 불가능한 기록은 삭제하지 않고 unverified로 격리
8. 기존 성과값 무효화
9. 정제된 체결만으로 포지션·손익·성과 재계산
10. 이관 전후 수량·현금·손익 차이 보고서 생성

오늘 LG생활건강처럼 가상 매도 후 가상 매수가 생긴 쌍도 실제 체결과 분리해야 합니다.

## 9단계: 시장·종목 사전검사

주문 직전 하나의 MarketPreflight를 반드시 통과하게 해야 합니다.

검사항목:

- 거래일 여부
- 정규장·시간외 구분
- 신규 진입 금지 시각
- 종목 거래정지
- VI 또는 변동성 중단
- 상·하한가
- 가격제한폭
- 올바른 호가단위
- 최소 주문수량·금액
- 매도 가능수량
- 공매도·신용 가능 여부
- 증거금률
- 시세 기준시각
- 마지막 Tick/호가 수신시각
- 시장 상태 조회 성공 여부

데이터가 없거나 조회에 실패하면 신규 위험 주문은 차단하고 청산 주문만 제한적으로 허용하는 fail-closed 정책이 필요합니다.

## 10단계: 시세 장애 보호

모든 주문 판단에 다음 필드를 저장합니다.

- 시세 제공자
- 데이터 기준시각
- 수신시각
- 지연시간
- 현재가
- 매수·매도호가
- 봉 확정 여부
- 시장 상태

보호 규칙:

- 시세가 허용 지연시간을 초과하면 신규 주문 금지
- WebSocket 단절 시 REST 확인 전까지 신규 주문 금지
- 연속 Tick 누락 또는 비정상 가격 점프 시 거래 중단
- 봉 전략은 미완성봉과 확정봉을 명시적으로 구분
- 당일 일봉을 사용하는 전략은 장중봉 사용 여부를 전략 계약에 선언

## 11단계: 주문 유형과 OCO

공통 주문 모델에 다음을 추가해야 합니다.

- MARKET
- LIMIT
- STOP
- STOP_LIMIT
- CONDITIONAL_LIMIT
- DAY
- IOC
- FOK

키움 계좌·시장별 지원 여부를 capability로 관리합니다. 지원하지 않는 주문 유형은 조용히 대체하지 말고 주문 전에 차단해야 합니다.

손절·익절은 OCO 그룹으로 관리합니다.

- 두 보호 주문이 동일 포지션·수량을 공유
- 하나가 체결되면 다른 주문 취소
- 취소 확인 전에는 추가 청산 주문 금지
- 부분체결 시 남은 포지션만큼 보호수량 정정
- 보호수량과 포지션 수량이 다르면 신규 매수 차단

## 12단계: 리스크 엔진 통합

모든 주문 경로가 같은 리스크 엔진을 통과해야 합니다.

필수 제한:

- 1회 최대 손실
- 일 최대 실현·평가 손실
- 종목당 최대 비중
- 전략당 최대 비중
- 섹터당 최대 비중
- 시장 전체 최대 투자비중
- 최대 동시 보유 종목
- 최대 미체결 매수금액
- 최대 단일 주문금액
- 연속 손실 한도
- 비정상 변동성
- 데이터 장애
- 미보호 포지션 존재
- 계좌 동기화 불일치
- 결과 불명 주문 존재

## 17단계: 안전한 배포 순서

권장 배포 단계는 다음과 같습니다.

### Phase A — 관찰 전용

- 신규 테이블과 상태 머신 추가
- 기존 주문 흐름은 유지
- 키움 주문·체결을 신규 원장에도 복제
- 주문은 보내지 않고 결과만 비교

### Phase B — Shadow 모드

- 기존 엔진과 신규 엔진이 주문 결정을 각각 계산
- 실제 주문은 기존 엔진만 전송
- 두 결과의 차이를 기록
- 계좌·포지션·리스크 계산 일치율 측정

### Phase C — 모의계좌 제한 적용

- 신규 엔진이 일부 전략만 주문
- 1종목 또는 매우 작은 수량
- 자동 재주문 금지
- 수동 승인 유지
- 매일 장 마감 후 원장 대조

### Phase D — 모의계좌 전체 전환

- 모든 주문 경로를 신규 서비스로 통합
- 기존 주문 코드는 읽기 전용으로 전환
- 최소 10~20 거래일 무인 운영
- 불일치 0건 확인

### Phase E — 실계좌 제한 전환

- REQUIRE_APPROVAL=true
- 종목 수와 주문금액 최소화
- 일손실·종목비중 보수적으로 설정
- 실시간 운영자 모니터링
- 자동 Kill Switch 검증

### Phase F — 자동화 확대

- 승인 자동화는 마지막 단계
- 각 전략별로 별도 활성화
- 이상 발생 시 즉시 이전 단계로 되돌릴 수 있어야 함

## 18단계: 배포 승인 조건

실계좌 적용 전에 아래 조건을 모두 만족해야 합니다.

- 실제 주문과 내부 주문 100% 연결
- 중복 주문 0건
- 원인 불명 체결 0건
- 가상 체결 생성 0건
- 거래일 지난 활성 주문 0건
- 포지션 수량 불일치 0건
- 미보호 포지션 0건
- 비용 출처 미확인 거래 0건 또는 명확한 추정 표시
- 모든 Timeout 장애 테스트 통과
- 재시작 복구 테스트 통과
- 동시성 테스트 통과
- 10~20 거래일 모의계좌 검증
- 롤백 절차 검증
- Kill Switch 실제 작동 확인
- 운영 대시보드와 알림 확인
- 전체 요구사항 추적표 100% 완료

핵심은 “기존 코드에 체크 로직을 계속 덧붙이는 것”이 아니라, 주문·체결·포지션을 하나의 검증 가능한 원장과 상태 머신으로 통합하는 것입니다. 가장 먼저 해야 할 실제 개발 단위는 신규 주문 원장 구축 → 기존 데이터 분류·이관 → 일반
주문 경로 통합 → 일관된 동기화입니다. 그 기반이 완성된 뒤 시장 보호, 리스크, 비용, 성과 기능을 올려야 전체 분석 내용을 빠짐없이 안전하게 적용할 수 있습니다.




현재 주문승인 탭은 “승인 목록 조회와 개별 주문 전송” 기능은 있지만, 운영자가 안전하게 판단하고 주문 생명주기를 추적하기에는 부족합니다. 가장 큰 문제는 승인 상태와 실제 주문·체결 상태가 한 화면에서 정확히 구분되지 않는다는 점
입니다.

운영 데이터 기준으로 API는 limit=50 요청에도 처리 가능 상태를 모두 합쳐 80건을 반환하고 있습니다. 오래된 실패 주문까지 계속 재처리 대상으로 노출됩니다.

## 최우선 P0 — 주문 사고 가능성

### 1. executed를 체결처럼 보이게 하는 상태 표시

현재 승인 상태는 키움이 주문을 접수하기만 해도 executed로 변경됩니다.

실제 사례:

- 승인 #393 코스맥스
- 승인 상태: executed
- 실제 주문 상태: open
- 체결수량: 0주

즉 화면의 “실행”은 체결이 아니라 주문 접수입니다. 운영자가 체결된 것으로 오해할 수 있습니다.

개선:

승인 상태: 대기 / 승인됨 / 거절 / 만료
주문 상태: 제출 중 / 접수 / 미체결 / 부분체결 / 체결 / 취소 / 거부 / 결과불명

두 상태를 별도 열로 표시해야 합니다.

주문 접수 성공 시 승인 행도 executed가 아니라 submitted 또는 order_submitted로 표시해야 합니다.

### 2. 실제 체결수량·잔여수량을 표에 표시

현재 표는 요청수량만 보여줍니다.

필수 표시:

- 요청수량
- 체결수량
- 잔여수량
- 주문가격
- 평균체결가
- 증권사 주문번호
- 마지막 동기화 시각

예:

요청 11주 / 체결 0주 / 잔여 11주
지정가 279,500원 / 평균체결가 -
주문번호 #0135745

부분체결이나 미체결을 한눈에 확인할 수 있어야 합니다.

### 3. 오래된 실패 주문의 무조건 재처리 차단

현재 API는 모든 failed 승인을 처리 가능 항목으로 반환합니다. 8월 18일의 실패 매도 주문도 8월 27일에 재처리 대상으로 나타납니다.

과거 매도 신호를 현재 계좌에 다시 실행하면 위험합니다.

개선 조건:

- 원래 신호의 유효기간 확인
- 현재 보유수량·매도 가능수량 재확인
- 현재 전략이 여전히 청산을 요구하는지 재평가
- 거래일이 바뀌면 기존 승인은 기본적으로 expired
- 재처리는 기존 주문 재전송이 아니라 새로운 승인 생성
- 원 승인과 재승인 연결
- 재처리 사유 기록

당일 주문도 일정 시간이 지나면 자동 만료해야 합니다.

### 4. 재처리 일괄 기본 동작 제한

현재 일괄 재처리는 화면에 표시된 재처리 버튼을 종목당 하나씩 자동 선택합니다. 사용자가 직접 주문을 선택하지 않아도 오래된 실패 주문들이 대상이 될 수 있습니다.

개선:

- 체크박스로 사용자가 명시적으로 선택
- 기본 선택 0건
- 날짜가 지난 주문은 선택 불가
- 종목, 수량, 현재 보유수량, 예상금액을 확인창에 표시
- 최종 주문 수량과 총액 표시
- 매수·매도 일괄 작업 분리
- 일괄 최대 금액·수량 제한
- 주문별 사전검사 결과 표시
- 실패 한 건 때문에 다른 주문이 잘못 재시도되지 않도록 독립 처리

취소후재처리 일괄은 특히 위험하므로 P0 수정 전에는 비활성화하는 편이 안전합니다.

### 5. 승인 유효기간과 가격 신선도

현재 대기 주문에는 등록시각만 표시되고 만료시각이 없습니다. 장 마감 직전 생성된 승인이 다음 거래일까지 남을 수 있습니다.

현재 대기 사례:

- #397 농심
- #399 신한지주
- #400 카카오
- 15:29경 등록

다음 날 승인하면 전일 신호와 전일 가격으로 주문할 가능성이 있습니다.

개선:

- expires_at 필수
- 장 마감 시 DAY 승인 자동 만료
- 승인 직전 현재가 재조회
- 신호가 대비 가격 변동률 표시
- 허용 범위를 초과하면 승인 차단
- 마지막 시세 기준시각 표시
- 미완성봉 신호 여부 표시
- 시장 개장 여부 표시

### 6. 오래된 미체결 주문의 차단 정보 정리

현재 승인 행에 다음 정보가 붙습니다.

증권사 미체결 49주 (#0019247)

그런데 이전 분석에서 과거 거래일 미체결 기록이 내부 DB에 계속 남는 문제가 확인됐습니다. 오래된 주문이 현재 승인의 차단 주문으로 연결될 수 있습니다.

개선:

- 당일 실제 키움 미체결 조회 결과만 차단 근거로 사용
- 과거 거래일 주문은 expired/canceled/unknown으로 종결
- 로컬 open 상태만으로 차단 주문 확정 금지
- 차단 주문의 거래일·주문시각·매수매도 표시
- “키움 확인 완료”와 “로컬 추정” 구분

- Kill Switch
- 최대 보유 종목 수

승인 버튼 옆에 다음과 같은 판정이 필요합니다.

사전검사 통과 9/9
주의 1건: 현재가가 신호가보다 1.8% 상승
차단 1건: 동일 종목 미체결 주문 존재

### 8. 손절·보호 주문 정보 표시

자율주문은 보호 상태를 관리하지만 주문승인 탭에는 보이지 않습니다.

매수 승인 전 표시:

- 진입가
- 손절가
- 목표가
- 1주당 위험
- 총 위험금액
- 체결 후 보호 방식
- Stop 주문 지원 여부
- 보호 실패 시 신규 매수 차단 여부

손절가가 없거나 보호 주문을 만들 수 없는 매수는 승인 버튼을 비활성화해야 합니다.

### 9. 주문 유형 명시

현재 가격이 0이면 사실상 시장가로 처리되는 구조가 있지만 화면에는 주문 유형 열이 없습니다.

필수 표시:

- 시장가
- 지정가
- Stop
- Stop Limit
- 조건부 지정가
- DAY/IOC/FOK
- 거래소

시장가 매도에서 가격이 0으로 보이면 데이터 오류처럼 보입니다. 시장가라고 명확하게 표시해야 합니다.

### 10. 매수와 매도의 위험도를 다르게 표현

현재 상태 색상 외에는 매수·매도 의미가 충분히 구분되지 않습니다.

권장:

- 신규 위험 증가 매수
- 기존 포지션 추가 매수
- 위험 축소 매도
- 전량 청산
- 손절
- 익절
- 리밸런싱

특히 손절·위험 축소 매도는 일반 매수보다 높은 우선순위로 상단에 배치해야 합니다.

### 11. 자율 관리주문과 일반 승인의 통합 표시 개선

현재 같은 탭에 두 종류가 섞여 있습니다.

- 자율주문: managed_order_id, decision_id, client_order_key 존재
- 일반 주문: 해당 필드 없음

백엔드 처리도 서로 다른 경로입니다.

개선:

- 공통 상태 모델로 통합
- 당장 통합이 어렵다면 관리주문과 일반 승인 탭 분리
- 주문번호, 결정 ID, 관리주문 ID 연결 표시
- 각 경로가 제공하는 안전장치 표시
- 일반 주문에는 중복방지 키 없음 같은 위험 상태 경고

### 12. 단일 승인에도 웹 확인 절차 적용

현재 안드로이드에서는 매수 승인 시 생체인증이 있지만 일반 웹에서는 승인 버튼 클릭 즉시 API가 호출됩니다.

개선:

카카오 64주 매수
지정가 38,400원
예상금액 2,457,600원
주문 후 예상비중 2.6%
손절가 36,100원
최대위험 147,200원

이 내용을 보여주는 확인 모달 후 최종 승인해야 합니다.

고액 주문, 시장가, 전량매도에는 주문명 또는 확인문구 입력도 고려할 수 있습니다.

## 중간 우선순위 P2 — 운영성과 가독성

### 13. 대기열과 이력을 분리

화면 제목은 “주문 승인 대기열”인데 실행·거절·실패·과거 실패까지 모두 표시합니다.

현재 API 동작:

- 최근 50건 조회
- 여기에 모든 pending, executing, failed를 추가
- 결과적으로 50건 제한을 초과
- 현재 운영 응답은 80건

개선:

- 대기: pending/executing
- 진행: submitted/open/partial/broker_unknown/cancel_pending
- 완료: filled/canceled/rejected/expired
- 오류: failed/unknown
- 서버 페이지네이션
- 상태별 개수 배지
- 기본 화면은 대기·진행만 표시
- 완료·과거 실패는 별도 이력 탭

limit은 실제 반환 건수에도 적용해야 합니다.

### 14. 필터와 정렬

필수 필터:

- 거래일
- 상태
- 매수·매도
- 전략
- 주문 유형
- 종목
- 일반/관리주문
- 차단 여부
- 재처리 가능 여부

권장 기본 정렬:

1. 손절·청산
2. 결과 불명
3. 부분체결
4. 취소 대기
5. 승인 대기
6. 신규 매수
7. 완료 이력

현재처럼 단순 ID 내림차순이면 중요한 손절 주문이 아래로 밀릴 수 있습니다.

### 15. 오류 메시지 사용자화

현재 다음과 같은 내부 오류가 그대로 표시됩니다.

approval revalidation failed: ApprovalBridgeError
Risk limit rejected buy: duplicate buy exposure already exists
Kiwoom kt10001 request failed

개선:

- 오류 코드
- 한국어 요약
- 실제 원인
- 사용자 조치
- 자동 재처리 가능 여부
- 증권사 원본 세부정보 펼치기

예:

중복 매수 차단
동일 종목에 미체결 매수 49주가 있습니다.
기존 주문 #0019247의 현재 상태를 확인한 후 처리하세요.

### 16. 종목명과 가격 표시 정상화

현재 신규 관리주문 일부는 종목명이 없어 종목코드가 이름으로 표시됩니다.

또한 가격이 다음처럼 부동소수점으로 내려옵니다.

- 38,390.99999999999
- 106,931.99999999999

국내 주문가격은 정수 호가로 저장하고 승인 생성 전에 호가단위로 정규화해야 합니다. 화면 표시 시점에만 반올림하면 실제 제출가격과 화면가격이 달라질 수 있습니다.

### 17. 자동승인 상태를 탭 내부에 명확히 표시

상단 다른 영역에는 자동승인 설정이 있지만 승인 탭 설명은 다음과 같습니다.

> 자동매매 신호를 즉시 전송하지 않고 승인 후 처리합니다.

자동승인이 켜져 있으면 이 설명은 사실과 다릅니다.

탭 상단에 다음을 표시해야 합니다.

자동승인: 켜짐
적용 대상: 일반전략 / 자율전략 / 전량매도
제외 대상: 수동 승인 필요 전략
최근 자동승인 결과: 성공 3 / 차단 2

자동승인 전환은 주문에 직접 영향을 주므로 별도 확인 모달과 감사 로그가 필요합니다.

## 낮은 우선순위 P3 — 관리 편의와 감사

### 18. 승인 상세 패널

행을 클릭하면 다음 전체 흐름을 보여주는 상세 패널이 필요합니다.

신호 → 후보 → 리스크 판정 → 승인 → 주문 요청
→ 주문번호 → 부분체결 → 완전체결 → 포지션 → 손익

표 한 행에 긴 전략 이유와 오류를 모두 넣으면 가독성이 떨어집니다.

### 19. 승인 감사 로그

추가할 항목:

- 승인자
- 승인 채널: 웹/안드로이드/자동
- 승인 시각
- 승인 당시 계좌 스냅샷
- 승인 당시 현재가
- 확인 모달 데이터
- 거절 사유
- 재처리 사유
- 설정 변경자
- 자동승인 정책 버전

현재는 수동승인, 자동승인 같은 문자열 중심이라 사용자·세션 단위 추적이 부족합니다.

### 20. 실시간 갱신

현재는 새로고침과 주문 처리 후 재조회 중심입니다.

개선:

- 대기 주문 생성 알림
- 주문상태 변경 실시간 반영
- 부분체결 수량 갱신
- 결과 불명 경고
- 데이터 마지막 갱신시각
- 자동 새로고침 중단 여부 표시

단, 실시간 표시를 추가해도 최종 상태는 키움 재조회 결과를 기준으로 해야 합니다.
